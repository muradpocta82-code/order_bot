# Order Bot: что осталось сделать (передача в новый чат)

Дата: **18.11.2026**. Проект: Telegram-бот заказов для оптового поставщика продуктов (HoReCa, Ташкент).
Этот файл — только **остаток** банка идей Claude (`IDEI_order_bot_2026-11-17.md`), уже сделанное перечислено
коротко, чтобы не делать заново.

## Часть 0. Чтобы новый чат сразу был в теме

**Где что.** Код на сервере `/opt/order_bot` (185.156.110.119), доступ с ноутбука владельца:
`~/order_bot_ssh '<команда>'` (SSH по ключу через туннель; при обрыве подождать 20–30 с и повторить).
Службы: `order_bot` (бот, пользователь **orderbot**), `order_bot_web` (мини-апп каталога, порт 8443),
`order_bot_backup.timer` (часовой `pg_dump` от postgres в `/var/backups/order_bot`),
`order_bot_verify.timer` (вс 03:30 проверка восстановления). Базы: `order_bot`, `order_bot_test`,
`order_bot_rehearsal`. Схема на версии **25**.

**Обязательный порядок работ.**
1. `cd /opt/order_bot && bash scripts/test_all.sh` → 147/0 · 82/0 · 16/0 + ruff `All checks passed`.
2. Миграция: сначала `bash scripts/rehearse.sh` (свежий дамп → order_bot_rehearsal от order_bot → миграции),
   потом боевая: `systemctl stop order_bot` → `venv/bin/python scripts/migrate.py` → `systemctl start order_bot`.
3. Проверка: `journalctl -u order_bot -n 30 --no-pager` (нет ERROR) и `venv/bin/python scripts/doctor.py` (нет ❌).
4. Каждая задача: запись в `CHANGELOG.md` + `git add -A && git commit && git tag deploy-ГГГГММДД-N`.
5. Отчёт владельцу — **одним предложением**, простыми словами.

**Жёсткие запреты.** Не трогать порт 443 и всё про VPN (wstunnel, xray, x-ui, vpn.sh, webroot).
Секреты в чат не выводить, `.env` целиком не читать. Широкие фильтры aiogram — только в `handlers_tail.py`
(подключается последним). Локальные файлы ноутбука не менять без просьбы. Один кусок работы за раз.

**Ключевые файлы.** `main.py` (13 циклов, меню команд), `orderbot/handlers.py` (ядро, 2.8 тыс. строк),
`orderbot/handlers_client.py`, `handlers_courier.py`, `handlers_reports.py`, `handlers_tail.py`,
`orderbot/db.py` (всё хранилище), `orderbot/ai.py` (Gemini; DeepSeek-ключ пустой намеренно, план Б — `nlu.py`,
`stt.py`/Vosk), `orderbot/summary.py`, `buylist.py`, `labels.py`, `pricecast.py`, `watch.py`, `docs/AGENT.md`.

**Уже сделано (не переделывать):**
A1 (бот не под root), A3-частично (git + теги), A5-частично (swap 2 ГБ, лимит журнала, MemoryMax),
A6 (тревога по частоте ошибок), A7 (doctor сверяет развёртывание), A10/A15 (проверено: локальный план Б,
нет eval/exec), A12 (`RUNBOOK_MANAGER.md`), B1 (`/buylist` + Excel), B2 (`order_events`, `/log`),
B4-частично (лимит долга, срок, напоминания, возраст долга), B5-частично (`/cost`, маржа по базе),
B7 (минимальный заказ уже был через `MIN_ORDER_USD`), B8-частично (±30 % в цене), C1 (утренние цены + «как обычно»),
C3 (`/for` — заказ за клиента текстом), C4-частично (`/invite`, `/refs`), C5-частично (решения по претензиям),

## Часть 1. Безопасность и надёжность (остаток волны 0)

### A2. Бэкапы вне сервера (осталось главное)
Сейчас: часовой `pg_dump` отдельным таймером в `/var/backups/order_bot`, 48 часовых + 30 дневных +
12 месячных, еженедельная проверка восстановления. **Нет копии вне сервера.**
Сделать: `rclone` (или Backblaze B2 / Cloudflare R2) раз в сутки, шифрование (`rclone crypt` или `age`),
ключ хранить **не на сервере**; после каждого бэкапа и проверки — пинг в Healthchecks, при ошибке `/fail`.
Готово, когда: файл появляется в облаке; `scripts/restore.py` поднимает базу из облачной копии;
пропавший бэкап даёт тревогу.

### A3. Остаток: репозиторий наружу и воспроизводимость
Есть локальный git с тегами `deploy-…`. Нет: удалённого репозитория (приватный GitHub/Codeberg, push с сервера
по deploy-ключу), `requirements.lock`, `.env.example` (только имена переменных), тега/откат встроенного
в `scripts/safe_deploy.py`. Готово, когда: свежий клон + `.env` + дамп = рабочий бот.

### A4. Внешний мониторинг (осталось подключить)
Готово: `GET /health` у каталога (200 + проверка БД), цикл `_heartbeat_loop` в `main.py`.
Нет: `HEARTBEAT_URL` в `.env` (Healthchecks.io, период 5 мин, grace 10 мин), проверка бэкапа в Healthchecks,
HTTP-проверка `https://littlemouse.su:8443/health` через UptimeRobot. Алерты владельцу — на почту/Telegram,
не через бота. Готово, когда: `systemctl stop order_bot` → владелец получает уведомление за ≤ 15 минут.

### A5. Остаток: память
Есть swap 2 ГБ, `vm.swappiness=10`, журнал 200 МБ, `MemoryMax` 900M/300M.
Нет: ленивая загрузка Vosk с выгрузкой после простоя; разбор, почему каталог (192 строки aiohttp)
занимает ~197 МБ (вероятно, тяжёлые импорты `orderbot` — см. G4).

### A8. Остаток: гигиена секретов
Есть `.env` 0600, владелец orderbot. Нет: `scripts/env_check.py` (печатает имена и длины, не значения);
перевыпуск ключей, если когда-либо печатались в чат; отдельный тестовый бот-токен для `live_*_check.py`;
регламент ротации (раз в полгода).

### A9. Остаток: сеть
Есть: вход только по SSH-ключу (`PasswordAuthentication no`, `PermitRootLogin prohibit-password`),
Postgres слушает 127.0.0.1, unattended-upgrades включён.
Нет осознанно: `ufw` — на сервере живут порты VPN/x-ui (443, 2096, 52077), включение файрвола может
отрезать владельца; решение за владельцем. Нет: fail2ban, проверки «ожидаемые порты» в `doctor.py`.

### A11. Остаток: тесты «нажми каждую кнопку»
Есть ruff `F821/F822/F823` в `test_all.sh` (нашёл 4 реальные ошибки в `onboarding.py`).
Нет: теста, который собирает все `callback_data` и команды из кода и прогоняет через `Dispatcher.feed_update`
с поддельным Bot и тестовой БД (ни одного исключения); отчёта `coverage` и списка непокрытых хендлеров.

### A13. Staging-бот по требованию
Отдельный тестовый токен + `order_bot_rehearsal`, юнит `order_bot_staging`, включать только на время
проверки (`systemctl start order_bot_staging`). `live_*_check.py` бьёт только по нему.

### A14. Учение «восстановление с нуля» + `bootstrap.sh`
`bootstrap.sh`: чистый Ubuntu → рабочий бот (пакеты, пользователь orderbot, venv из lock-файла, юниты и
таймеры, certbot-хук, восстановление дампа). Раз в квартал — прогон на одноразовом VPS, замерить время
восстановления (цель ≤ 2 часа). Частично помогает уже готовый `scripts/rehearse.sh`.

## Часть 2. Деньги владельца

### B3. Книга расчётов (`payments` + `allocations` + `credit_notes`) — крупная задача
Сейчас оплата — поля заказа (`paid_amount`, `payment_method`, `paid_at`): один платёж на заказ.
В опте клиент платит одной суммой за неделю, частично, с зачётом претензии. Нужны таблицы
`payments(id, client_id, amount, currency, method, ts, note)`, `allocations(payment_id, order_id, amount)`
(зачёт по FIFO), `credit_notes`; `/debt` и `/settle` читают из книги; миграция с бэкфиллом из `orders`.
Делать по шагам: сначала чтение (отчёт из новой книги = отчёт из старых полей), потом переключение.
Готово, когда: оплата одной суммой за 3 заказа и частичная оплата работают, баланс сходится с ручным.

### B4. Остаток: акт сверки и кредит-ноты
Есть: `credit_limit`, `credit_days`, предупреждение при превышении лимита, напоминания должникам раз в день,
возраст долга в `/debt`. Нет: PDF «Акт сверки» за период (`fpdf2` + `invoice.py` уже есть), кредит-нот
(решение по претензии «кредит» пока только фиксируется), напоминаний «плательщику» (см. C6).

### B5. Остаток: маржа по дате и диктовка закупок
Есть: `cost_prices` (история закупок с датой), `/cost позиция цена`, `/margin` по последней закупке.
Нет: расчёта маржи по закупке **на дату заказа** (`db.cost_on` есть, `sold_items` не отдаёт дату позиции);
ввода закупок голосом («помидоры 8500, лук 3200»); предупреждения «маржа ниже порога» / «отрицательная»
в отчёте по позициям.

### B6. «Цены на завтра» за 2 минуты
Бот предлагает новый прайс = закупка × наценка по категории (правила в `settings`), показывает ↑/↓ и %,
менеджер жмёт «Опубликовать» или правит строки; запись в `price_versions` (`/price_undo` уже есть);
напоминание, если прайс не обновлялся N дней.

### B7. Остаток: доставка
Есть минимальная сумма заказа (`MIN_ORDER_USD`). Нет `free_delivery_from` и `delivery_fee`
(порог бесплатной доставки, плата за доставку в заказе и в накладной).

### B8. Остаток: страж опечаток
Есть проверка цены ±30 % в `/price_set`. Нет: проверки количества в заказе (> 3× максимум клиента
по этой позиции или жёсткий потолок → уточнение клиенту); защиты от дубля (тот же клиент, те же позиции,
меньше 10 минут → «похоже, вы уже отправили этот заказ»).

### B9. Усушка и списания
`/writeoff позиция количество причина` (голосом тоже), привязка к `stock_items`, отчёт «потери % по категории».
Без этого маржа по овощам и зелени завышена.

### B10. Курс USD
Хранить `usd_rate_at_order` в заказе и сумму в сумах на момент подтверждения; клиенту показывать сумму
в сумах, USD — менеджеру; таблица `rate_history`; смена курса не меняет суммы подтверждённых заказов.

### B11. Спрос без предложения
`missing_items` уже копит фразы. Добавить `missing_requests(user_id, phrase, ts)`, еженедельный дайджест
менеджеру «топ-10 запросов, которых нет в прайсе» с кнопкой «Добавить в каталог», и сообщение тем,
кто просил, когда позиция появилась.

### B12. Закупка по поставщикам
`catalog.supplier`; `/buylist` делится по поставщикам, каждая часть — готовое сообщение для пересылки;
позже сравнение цен поставщиков.

### B13. Цены и скидки по клиентам
`client_prices(client_id, catalog_id, price)` или `discount_pct` по клиенту/категории; мини-апп и черновик
берут цену клиента. Делать, когда клиентов ≥ 5.

### B14. «Горячее предложение» на скоропорт
`/hot позиция цена до_времени` → рассылка выбранным клиентам с кнопкой «Взять N кг»; конверсия пишется в события.

## Часть 3. Клиенты

### C2. Умный черновик по расписанию клиента
По истории (`orders`, уже есть `rday` и `user_weekdays`): если клиент обычно заказывает по средам и не заказал,
бот присылает собранный черновик с вопросом «Отправить?». Работает с 3+ заказами. Без LLM.

### C4. Остаток: бонусы за приглашения
Есть `/invite` и `/refs` (кто кого привёл). Нет автоматического бонуса: скидка на следующий заказ или
бесплатная доставка после первого заказа приглашённого (решение о размере — за владельцем).

### C5. Остаток: претензии «в два нажатия»
Есть: «Есть проблема» → текст → решения кнопками (заменить/кредит-нота/отклонить) → ответ клиенту.
Нет: кнопок [Всё хорошо] [Есть проблема] через 24 часа после доставки; выбора позиции и типа проблемы
(недовес / качество / не привезли / другое) кнопками; фото к претензии; автозачёта кредит-ноты в следующий счёт
(зависит от B3).

### C6. Роль «плательщик»
Повар заказывает, платит бухгалтер/владелец. Второй Telegram-аккаунт на точку получает накладные,
напоминания о долге и акты сверки, но не заказывает. Таблица `venue_contacts(user_id, venue_id, role)`.

### C8. Правила замены позиций
«Если нет — заменить на … / не заменять / спросить» на клиента/позицию; правило видно упаковщику на карточке
и срабатывает в диалоге «похожая позиция».

### C9. Остаток: двусторонняя связь с менеджером
Есть: клиент пишет через кнопку «☎️ Менеджер», сообщение уходит менеджеру. Нет ответа менеджера из бота
клиенту (привязка к заказу, скрытый номер). Сделать `/reply <client_id> текст` или ответ реплаем на пересланное.

### C10. Остаток: алерты «давно не заказывал»
Есть общий `_churn_loop` (10+ дней). Нет: медианного личного интервала клиента, алерта «X не заказывал 9 дней,
обычно каждые 4» с кнопкой «Отправить мягкое напоминание» (и само напоминание).

### C11. Несколько точек у одного клиента
`venues(id, name, address, lat, lon, payer_id)`, у пользователя список точек, выбор точки при заказе,
сводный счёт на сеть. Сейчас 1 user = 1 повар = 1 адрес.

### C12. Геопин и статус доставки
Просить геопин при онбординге (`lat/lon`), курьеру — «Открыть в картах», клиенту при «Выехал» — окно
прибытия по слоту и предупреждение об опоздании. (Нужно для D5.)

### C13. Остаток: метрики оценок
Есть оценка 1–5 и причина при ≤ 3. Нет средней оценки курьера/упаковщика и доли недовольных в недельном отчёте
(в `/ops` пока только претензии и недоставки).

### C14. Онбординг нового клиента за 60 секунд
Сейчас: 4 базовых вопроса и ручное одобрение менеджером. Улучшить: карточка менеджеру с кнопками
[Допустить + срок кредита] [Отклонить] [Позвонить]; приветствие в 3 строки с примером заказа и кнопками;
воронка в отчёте (заявок → допущено → первый заказ → активные). Готово, когда новый повар делает первый заказ,
не позвонив менеджеру.

### C16. Подтверждение суммы и окно правок
Показывать итог в сумах (после B10), слот, «изменить можно до HH:MM» (отсечка есть), честно говорить,
на какой день уйдёт заказ, пришедший после отсечки.

### C7. Узбекский язык — **отменён владельцем** (16.11.2026). Не делать, пока он сам не попросит.

## Часть 4. Упаковщик и курьер

### D4. Несколько упаковщиков и курьеров, смены
Роли owner/manager/packer/courier в `staff.role`, переключатель «на смене», назначение заказа вручную или
по кругу, эскалация, если исполнитель молчит N минут (расширить `_escalation_loop`). Менеджер и курьер
из `.env` остаются «владельцем доступа».

### D5. Маршрут курьера
Сортировка доставок: слот → ближайший сосед по координатам (гаверсинус, без платных API), ссылка «Весь маршрут»
одним сообщением. Требует C12 (координаты).

### D7. Остаток: перенос недоставки
Есть причины кнопками и запись в историю. Нет кнопки «перенести на дату» прямо из «Не доставлено»
(сейчас только через смену даты упаковщиком).

### D9. Тихие часы и пакетные уведомления
Менеджер не должен получать 12 карточек в 22:00. После отсечки — одно сообщение «12 заказов на завтра:
[Открыть очередь]» (`/queue` уже есть); тревоги (аварии, ошибки) — сразу; обычные — пакетом утром;
тихие часы настраиваются в `settings`.

## Часть 5. Качество разбора и ИИ

### E2. Golden-набор из боевых данных
Кнопка менеджеру «Запомнить как пример» при правке разбора: пара «текст → правильные позиции»
(без имён и телефонов) в `tests/orders_golden_live.jsonl`; `eval_parse.py` перед правкой промпта/парсера;
деплой блокируется, если точность упала больше чем на 2 пункта.

### E3. Общие синонимы (словарь)
`aliases` сейчас личные (по `chef_id`). Добавить общий словарь (русский сленг, опечатки, узбекские названия —
словарь, а не интерфейс). Если 3 разных повара привязали фразу к одной позиции — предложить менеджеру
«сделать общим». Замер на golden до/после.

### E4. Остаток: учёт стоимости ИИ
Есть кэш (sha1 текста, 7 дней в памяти), `LLM_DAILY_BUDGET`, `LLM_USER_HOURLY`.
Нет: таблицы `llm_usage(day, provider, calls, tokens, est_cost)`, предупреждения на 80 % бюджета,
счётчика «заблокировано вызовов», строки «стоимость ИИ на заказ» в `/health` и недельном отчёте.

### E5. Уточнения пакетом
Вместо цепочки «вопрос → ответ → вопрос» — одно сообщение с несколькими строками и кнопками
(«Помидоры: 5 кг / 10 кг / другое»). Цель по метрике E1: ≤ 2 вопроса на заказ.

### E6. Фасовки данными, а не кодом
`units.py` содержит правила; вынести `pack_unit`, `pack_size`, `step` в колонки прайса,
чтобы менеджер правил в Excel без деплоя.

### E7. Провайдер ИИ как настройка + сравнение «цена/качество»
Обёртка в `ai.py`: провайдер и модель в `.env`; скрипт гоняет golden-набор по кандидатам и печатает точность,
задержку, стоимость заказа; выбирается самый дешёвый при точности не ниже порога.

### E8. Голос: метрика распознавания
Показ распознанного текста уже есть в статусе. Нет: кнопок [Верно] [Исправить] и счётчика доли «Исправить»
отдельно для Gemini и Vosk.

### E9. Фото-списки
Отдельная метрика качества для `source = photo`; если низкая — подсказка «лучше текстом или голосом»
и ручной разбор менеджером.

### E10. Теневой режим промптов
Новый промпт параллельно разбирает 10 % боевых заказов, результат только логируется; сравнение с боевым
до включения. Требует E1 (уже есть) и аккуратной работы с бюджетом ИИ.

## Часть 6. Аналитика и панель владельца

### F2. Выгрузка в Google Sheets / Looker Studio
Ночью `gspread` (сервисный аккаунт) выгружает `orders`, `order_items`, платежи, долги, клиентов, события
в листы; владелец строит сводные и графики сам. Metabase и подобное не ставить (память).

### F3. Мини-апп владельца (после F2)
Страница в существующем aiohttp: сегодня, долги, касса, график недели. Вход только по подписи Telegram
и только для id владельца/менеджера. Графики без внешних CDN.

### F5. Остаток: недельный отчёт «к прошлой неделе»
Отчёт есть. Нет сравнения с прошлой неделей (выручка, заказы, маржа, долги, правки, претензии)
и блока «3 вывода / 3 действия», посчитанных правилами без LLM.

### F6. Карточка клиента `/client <id>`
Один экран: заказов и сумма, частота, средний чек, долг и его возраст, любимые позиции, претензии, оценка,
заметка (`/note` уже есть), последняя активность, кто привёл (`/refs`).

### F7. Остаток: маржа по срезам
Есть `/margin` за период. Нет трёх срезов (по позиции / категории / клиенту) и списка убыточных
и низкомаржинальных позиций с объёмом.

### F8. Прогноз закупки — **не раньше 8 недель данных**
Скользящее среднее по дню недели на позицию с учётом выходных; сначала как подсказка рядом с `/buylist`,
не как автозаказ.

## Часть 7. Каталог, мини-апп, склад

### G4. Каталог без тяжёлых импортов
При публикации прайса бот пишет `data/catalog.json` (позиции, единицы, цены, категории); сервер каталога
читает только JSON и БД (проверка `initData`, приём заказа) и не импортирует `orderbot` целиком.
Цель: RSS каталога < 80 МБ (сейчас ~197 МБ). Заодно проверить открытие мини-аппа на живых телефонах
(iPhone/Android, мобильный интернет) — если у кого-то не открывается, вариант Cloudflare Tunnel
на поддомен (порт 443 и VPN не трогать).

### G5. Счётчик открытий мини-аппа
`webapp_events(user_id, ts, kind[open|add|order])`. Если за 4 недели открытий почти нет — отключить мини-апп
(минус ~200 МБ памяти и поддержки), оставить текстовый каталог.

### G6. Остаток: остатки → автоскрытие и замены
Есть `/stop`, `/unstop`, `/stoplist` (ручной стоп-лист). Нет: автоматического скрытия при `stock_left = 0`,
предупреждения менеджеру о подходе к порогу и предложения замены клиенту (через C8).

### G7. Приход товара голосом
«Приход: помидоры 120 кг по 8200, огурцы 80 кг по 9000» → остатки + закупочные цены (`cost_prices` уже есть),
позже учёт поставщиков (B12).

### G1. Payme/Click через Telegram Payments — **платно, только с согласия владельца**
Нужен мерчант-аккаунт и договор. Проверять актуальность провайдеров в @BotFather → Payments.
Сторонние PyPI-пакеты «для Payme/Click» без разбора кода не ставить.

### G3. Проверка чека по фото
Клиент присылает фото чека → vision-модель вытаскивает сумму/дату, бот сверяет с заказом и помечает
«совпало / проверить», менеджер подтверждает кнопкой. Результат модели — только подсказка.

### G2. USDT — заморожено
Новых функций вокруг TON/USDT не добавлять до юридического ответа (см. Часть 9).

### G9. ЭСФ/налоги — не код, вопрос бухгалтера.

## Часть 9. Код и процесс

### I1. Дальше резать `handlers.py` (2774 строки)
Только механические переносы, по одному куску: поток заказа, панель менеджера, правки, PDF, оплата →
`test_all.sh` после каждого → деплой. `handlers_tail.py` подключать последним, как сейчас.

### I2. Удалить легаси SQLite/pg8000
Сначала `coverage` по трём наборам тестов, потом удалить неисполняемые ветки: `aiosqlite`, `pg8000`, `pg.py`,
`backup.py`, SQLite-ветки в `db.py`. Перед удалением — git-тег.

### I3. Токены подтверждения цены из памяти в БД
`orderbot/state.py` держит `pending_prices` в памяти: после перезапуска подтверждение теряется.
Перенести в таблицу/`chat_state` с TTL, проверить тестом «рестарт в середине подтверждения».

### I4. Postgres под 1.9 ГБ
Проверить `shared_buffers`, `work_mem`, `max_connections`, размеры `psycopg_pool` (бот + каталог ≤ 10–15
соединений), включить `pg_stat_statements`, раз в месяц смотреть топ-5 медленных запросов.

### I5. Тексты и пороги без деплоя
Тексты сообщений (`texts.py`, части `formatting.py`) и пороги из раздела B — в `settings` или файл,
чтобы владелец/менеджер правил командой.

### I6. Типы на деньгах
`mypy`/`pyright` только на модули с деньгами и датами (`db.py` суммы, `drafts.py`, `tonpay.py`, `clock.py`),
запрет `float` на деньгах проверять автоматически.

### I7. Гонки при нажатиях
`transition_order` уже атомарен (`WHERE status = ...`). Осталось: тест на параллельные нажатия двух людей
по одному заказу и проверка остальных переходов оплаты (`mark_order_paid`, `apply_ton_payment`).
